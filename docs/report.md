### 사실 (서버 요청 기록)

### 원인 (코드로 확인한 연쇄)
1. **비용만 저장해도 하루 기록 줄이 생긴다** — 정비/주유/기타 저장은 그날 `daily_logs` 줄이 없으면 빈 기록(휴무 아님·횟수 0)으로 만든다
   (`syncExpenseItems.js` `ensureDailyLog`, `syncExpenseRecords.js`→`upsertDailyLog`). 비용 행은 이 줄에 `daily_log_id`로 묶이고 삭제가 연쇄된다.
2. **불러오면 그 빈 줄이 일지 기록으로 들어온다** — `hydrateMergeWork.js:37-49`가 `daily_logs` 모든 줄을 일지 기록(`fixedCount 0`)으로 만든다.
3. **일지 자동 저장이 그날을 "빈 날"로 지운다** — `useDayDraft.js` 자동 저장 → `saveDayRecord`(`day-record.js:163`)가 휴무 아님·횟수 0·파렛트 0·콜 0이면
   그 날짜를 지우고(정비/주유/기타는 판정에 안 들어감), `dayLogCloudCommit.js` `writeDayKeyToServer`가 "전에는 있었는데 지금 없음"이라 `deleteDayLogOnServer`로
   서버 `daily_logs`를 지운다(`dayLogCloudCommit.js:80`) → 연쇄로 비용 삭제.
4. **왜 열기만 해도 자동 저장이 돌았나** — `useDayDraft.js:150-153`은 "처음 한 번은 저장 안 함"을 `isFirstDraftRef`로 막지만, 개발 모드의 React
   `StrictMode`(`main.jsx:12`)가 화면을 열 때 이 처리를 두 번 돌려 첫 번째가 그 표시를 써 버리고 두 번째가 600ms 뒤 저장을 건다 → 개발 서버에서는
   **일지 화면을 열기만 해도** 3번이 일어난다(9/30에 "저장 중…"이 뜬 것과 일치).
   배포(실사용) 빌드는 `StrictMode`가 두 번 돌리지 않아 "열기만 해서"는 안 생기지만, **운행 없는 날에 휴무를 눌렀다 풀거나 횟수를 넣었다 0으로 되돌리는 등
   그날을 빈 날로 만드는 편집**을 하면 똑같이 그날 비용이 사라진다.
- 같은 삭제 코드가 있는 곳: `syncDeletedWorkDates.js:46` — **앱 어디서도 부르지 않음**(grep 결과 호출부 0, 자기 테스트만) → 실제 위험 없음. `directMutations.js:34`(차량 삭제 — 차량과 함께 지우는 게 의도라 해당 없음).
- 영향 범위: 차량 무관(차주 메인·서브·연동 기사 모두), 운행 없이 비용만 있는 날.

## 배포까지 순서 0-3-A — 그날 비용이 남아 있으면 서버 하루 기록 줄을 지우지 않는다 `[x]` (착수지시서 확정 2026-09-30)

> 진행(2026-09-30): 코드 커밋 react-app `1f1b4a2`. 브라우저 확인 통과(아래). **push·CI 대기** → 최종 `[x]` 승인.

### 1. 목적 (쉬운 말)
일지에서 어떤 날이 "빈 날"이 되어도, 그날 정비/주유/기타가 하나라도 있으면 서버의 하루 기록 줄을 **지우지 않고 빈 기록으로 남긴다**.
그래서 그날 비용이 함께 사라지지 않는다. 비용이 하나도 없는 날은 지금처럼 줄을 지운다.

### 2. 현재 → 목표
| | 현재 | 목표 |
|---|---|---|
| 일지가 빈 날로 저장될 때 | 그날 콜 상세 삭제 → `daily_logs` 줄 삭제 → 서버 연쇄로 비용 삭제 | 콜 상세 삭제 → 그날 그 차량 정비·유류·기타 행이 **있으면** 줄을 빈 기록(휴무 아님·횟수 0·파렛트 0)으로 고침, **없으면** 지금처럼 삭제 |
| 화면(store) | 그 날짜 일지 기록 삭제 | 그대로(화면은 빈 날). 다음 불러오기 때 빈 기록으로 다시 들어오고, 또 빈 날로 저장돼도 위 규칙이라 안전 |

### 3. 건드릴 파일 (react-app)
1. `src/lib/dailyLogRemoval.js` **(신규)** — "그 날짜 서버 하루 기록 줄 지우기(비용 있으면 빈 기록으로 남기기)" 함수 1개.
2. `src/lib/dayLogCloudCommit.js`(**209줄, §6 초과**) — `deleteDayLogOnServer`(73~82줄)를 위 새 파일로 옮기고 import 1줄 → **200줄**.
   **분리설계안:** 책임 경계 = "서버 하루 기록 줄을 언제 지우고 언제 남기나"라는 삭제 규칙은 새 파일 전담, `dayLogCloudCommit.js`는 날짜별 쓰기 흐름만. 의존성: `dayLogCloudCommit.js` → `dailyLogRemoval.js` → `supabaseClient.js`(한 방향). 기계적 절단 아님(삭제 규칙이 이번에 커져서 분리).
3. 테스트: `src/lib/dailyLogRemoval.test.js`(신규), `src/lib/dayLogCloudCommit.test.js`(빈 날 저장 시 비용 있으면 줄 유지 1개 추가).

### 4. 안 건드릴 것 (근거)
- `syncDeletedWorkDates.js` — 호출부 0(grep). `day-record.js`의 빈 날 판정 — 화면(store)에서 빈 날을 지우는 건 그대로 두고 서버 줄만 보호(화면·계산 무영향).
- 비용 저장 경로(5-A·5-B)·불러오기·서버(DB) — 무변경.

### 5. §8 5대 질문
1. 구독 화면 무변경. 2. 보이는 값 = store. 3. 쓰기 창구: 일지 자동 저장 → `commitMainDayLogToCloud` 1곳. 4. 동시편집: 확인과 삭제 사이에 상대가 그날 비용을 새로 넣으면
   그 비용이 지워질 수 있는 짧은 틈이 남음(서버 한 번에 처리하려면 DB 함수 필요 — 이번 범위 밖, 알려진 한계). 5. 권한: 차주·연동 기사 모두 그 차량 `daily_logs` 수정 허용(5-B 조사 3).

### 6. 기대 동작
- 운행 없고 비용만 있는 날의 일지를 빈 날로 저장해도 그날 비용이 서버에 남는다.
- 비용도 없는 빈 날은 지금처럼 서버 줄이 지워진다. 운행이 있는 날 저장은 무변경.

### 7. 실패 시 처리
기존과 같음: 서버 오류 → 던져서 일지 "저장 실패" 표시·토스트, store는 저장 전 값. **신규 레이어 없음, DB 변경 없음.**

### 8. §6 200줄
`dayLogCloudCommit.js` 209 → 200(위 분리설계안). 신규 `dailyLogRemoval.js` 40줄 안팎.
