## 배포까지 순서 5-B — 연동 차량 정비/주유/기타 항목 단위 저장 — 조사 기록

권한 `[확인: 2026-09-27]`: 연동 차량의 정비/주유/기타는 차주·기사가 서로의 항목을 보고·고치고·지우는 한 장부(`docs/roadmap.md` 5번).

### 조사 1 — 코드에서 확인한 현재 상태
- **저장 방식:** 차주·기사 모두 "그 차량의 날짜별로 전부 지우고 내 목록 다시 넣기"(`syncExpenseRecords.js`). 행 삭제는 `daily_log_id` 기준이라 누가 쓴 행인지 안 가림.
- **차주 → 연동 차량:** 차주가 넣은 연동 서브 항목은 아직 메인 칸에 저장(5-A 규칙). 기사 입력 항목은 매출 합계에만 쓰이고
  **목록 화면 어디에도 안 보임**(`driverExpenses` 사용처는 `OwnerRevenueView.jsx`뿐) — 차주가 보고·고치고·지우려면 화면 쪽 작업도 필요.
- **기사 → 자기 차량:** 배정 차량 칸 전체를 불러옴(`hydrateEmployedDriver.js:57`) → 차주가 그 차량 칸에 넣은 항목도 기사 목록에 들어옴(차량 표시 붙은 채 → 기사 본인 매출에선 빠짐, 5-A-2 한계).
- **서버 권한(RLS)** — 저장소에 기록이 없어 조사 3에서 서버에 직접 확인.


### 조사 3 — 서버 회신 결과 (2026-09-27, 사용자 실행)
- **권한(RLS):** 정비·유류·기타 세 표 모두 조회·수정·삭제 = "내가 쓴 행" 또는 "내 소유 차량" 또는 "내가 `linked` 기사인 차량"이면 허용.
  작성 = 쓴 사람이 나(`user_id = auth.uid()`)이고 그 차량이 내 소유이거나 연동 차량일 때. `daily_logs`도 같은 구조.
  → **차주·연동 기사는 서버상 이미 서로의 행을 보고·고치고·지울 수 있다(확인된 권한과 일치). DB 변경 불필요.**
  → 동시에 **지금의 "날짜별 전부 지우고 다시 넣기"는 실제로 상대 행을 지운다**(위험 확정).
- **칸:** 각 행 `id`(uuid, 서버 자동) + `daily_log_id`·`user_id`·`vehicle_id`·`work_date`·`sequence`·금액칸·`raw`(jsonb). 앱 항목 id는 `raw.id`에만 있고 고유 조건 없음.
- **키:** `daily_logs`는 (차량, 날짜) 고유 — 같은 날은 차주·기사가 한 줄을 공유. 세 표의 `user_id`가 `profiles`에 `ON DELETE CASCADE`
  → **쓴 사람 계정이 삭제되면 그 사람이 입력한 항목도 서버에서 함께 삭제된다**(공용 장부와 충돌 — 사용자 결정: 고친다, 5-C).

- **항목 id 없는 옛 행(사용자 조회):** 유류 0/2, 정비 **3/6**, 기타 0/1. → 서버 변경 없이, 불러올 때 쓰는 임시 id 계산(`maint-날짜-순번`, `expenseFrom*Record`)을
  저장 때도 똑같이 써서 찾는다. 고치면 `raw.id`가 채워져 이후 고정된다.

### 결정 `[확인: 2026-09-27]`
1. 설계 "연동 차량은 항목 id 기준으로 바뀐 것만 넣고·고치고·지우기" + 슬라이스 2개(5-B-1 기사 쪽 → 5-B-2 차주 쪽).
2. 계정 삭제 시 입력 항목이 함께 지워지는 서버 설정은 **고친다** — DB 변경이라 5-B 뒤 별도 슬라이스 5-C.

## 배포까지 순서 5-B-2 — 차주가 연동 차량 정비/주유/기타를 기사와 한 장부로 보고·고치고·지우기 `[x]` (착수지시서 확정 2026-09-30)

> 완료(2026-09-30): react-app `c573434`, 브라우저 확인·push·CI 초록·§5 리뷰 통과·사용자 최종 승인.

### 1. 목적 (쉬운 말)
차주가 연동 차량에 넣는 항목을 그 차량 칸에 **바뀐 것만** 저장하고, 기사가 넣은 항목도 차주의 정비/주유/기타 화면에 보여 차주가 고치고 지울 수 있게 한다.
지금까지 메인 칸에 잘못 쌓인 연동 차량 옛 항목은 그 차량 칸으로 옮긴다.

### 2. 현재 → 목표
| | 현재 | 목표 |
|---|---|---|
| 차주 저장(연동 서브 표시 항목) | 메인 칸에 날짜별 방식(5-A 규칙) | 그 연동 차량 칸에 **항목 단위**(`syncExpenseItemsForVehicle`, 5-B-1과 같은 규칙). 메인 칸의 그 날짜는 5-A처럼 정리 |
| 옛 항목 옮기기 | — | 연동 차량 칸에 없는데 **메인 칸에 같은 id가 있는 항목**은 "옛 항목"으로 보고 연동 칸에 넣는다(메인 칸에서 저장할 때 한 번 더 확인). 메인에도 없으면 상대가 지운 것 → 되살리지 않음(5-B-1 규칙 유지) |
| 차주 불러오기(연동 서브 칸) | 읽기 전용 기사 내역(`driverExpenses`) — 목록 화면에 안 보임 | **차주 목록**(차량 표시 붙음, id 중복 제거) → `/app/logs/차량번호/expenses`·일지 화면에 기사 항목도 보이고 고치기·지우기 가능 |
| 매출 "기사" 탭 | 읽기 전용 기사 내역 + 차주 목록 서브 표시 항목(5-A-2) | 규칙 그대로 — 기사 항목이 차주 목록 쪽으로 옮겨 올 뿐 합계 동일(이중 계산 없음) |

### 3. 건드릴 파일 (react-app)
1. `src/domain/expenseVehicleRouting.js`(70줄) — 연동 서브 표시 항목도 그 차량 대상으로 나누고 "항목 단위" 표시를 붙인다. 메인 정리 날짜에 포함.
2. `src/lib/syncExpenseItems.js`(140줄) — 선택 옵션 "옛 항목 찾을 칸(메인 차량 id)" 추가: 안 바뀐 항목이 연동 칸에 없을 때 메인 칸에 같은 id가 있으면 넣는다.
3. `src/lib/expenses.js`(57줄) — 차주 경로에서 "항목 단위" 대상은 `syncExpenseItemsForVehicle`(이전 목록 = 저장 전 화면 값 중 그 차량 표시 항목), 나머지는 5-A 방식. 순서는 서브 먼저·메인 나중 유지.
4. `src/lib/hydrateOwnerDriverExpenses.js`(69줄) — 연동 서브 칸도 차주 목록으로(읽기 전용 목록은 빈 배열).
5. 테스트: `expenseVehicleRouting.test.js`·`syncExpenseItems.test.js`·`cloudMemorySave.test.js`·`hydrate.test.js`.
   **기존 기대값 변경(사전 보고):** 5-A 테스트 2개 — "연동 서브 표시 항목은 메인 칸에 남는다"(`expenseVehicleRouting.test.js`·`cloudMemorySave.test.js`)와
   "연동 서브 칸은 읽기 전용"(`hydrate.test.js`)은 5-B 전까지의 규칙이라 새 규칙으로 바꾼다.

### 6. 기대 동작
- 차주 화면(연동 차량 정비/주유/기타)에 기사가 넣은 항목이 보이고, 차주가 고치고 지울 수 있다. 기사 화면에도 반영된다.
- 차주가 연동 차량에 넣은 항목은 그 차량 칸에 저장되고, 기사가 저장해도 안 지워진다(5-B-1과 맞물림).
- 메인 칸의 연동 차량 옛 항목은 차주가 한 번 저장하면 그 차량 칸으로 옮겨진다(화면 목록은 그대로, 중복·유실 없음).
- 매출 합계(차주·기사·전체 탭)는 지금과 같다.

### 7. 실패 시 처리
기존과 같음: 오류 → 토스트, store 저장 전 값. 서브 먼저·메인 나중이라 중간 실패 시 최악은 두 칸 중복(불러올 때 id로 하나만). **신규 레이어 없음, DB 변경 없음.**
