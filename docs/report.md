## 배포까지 순서 5-B — 연동 차량 정비/주유/기타 항목 단위 저장 — 조사 기록

권한 `[확인: 2026-09-27]`: 연동 차량의 정비/주유/기타는 차주·기사가 서로의 항목을 보고·고치고·지우는 한 장부(`docs/roadmap.md` 5번).

### 조사 1 — 코드에서 확인한 현재 상태
- **저장 방식:** 차주·기사 모두 "그 차량의 날짜별로 전부 지우고 내 목록 다시 넣기"(`syncExpenseRecords.js`). 행 삭제는 `daily_log_id` 기준이라 누가 쓴 행인지 안 가림.
- **차주 → 연동 차량:** 차주가 넣은 연동 서브 항목은 아직 메인 칸에 저장(5-A 규칙). 기사 입력 항목은 매출 합계에만 쓰이고
  **목록 화면 어디에도 안 보임**(`driverExpenses` 사용처는 `OwnerRevenueView.jsx`뿐) — 차주가 보고·고치고·지우려면 화면 쪽 작업도 필요.
- **기사 → 자기 차량:** 배정 차량 칸 전체를 불러옴(`hydrateEmployedDriver.js:57`) → 차주가 그 차량 칸에 넣은 항목도 기사 목록에 들어옴(차량 표시 붙은 채 → 기사 본인 매출에선 빠짐, 5-A-2 한계).
- **서버 권한(RLS)** — 저장소에 기록이 없어 조사 3에서 서버에 직접 확인.


### 조사 3 — 서버 회신 결과 (2026-09-27, 사용자 실행)
- **권한(RLS):** 정비·유류·기타 세 표 모두 조회·수정·삭제 = "내가 쓴 행" 또는 "내 소유 차량" 또는 "내가 `linked` 기사인 차량"이면 허용.
  작성 = 쓴 사람이 나(`user_id = auth.uid()`)이고 그 차량이 내 소유이거나 연동 차량일 때. `daily_logs`도 같은 구조.
  → **차주·연동 기사는 서버상 이미 서로의 행을 보고·고치고·지울 수 있다(확인된 권한과 일치). DB 변경 불필요.**
  → 동시에 **지금의 "날짜별 전부 지우고 다시 넣기"는 실제로 상대 행을 지운다**(위험 확정).
- **칸:** 각 행 `id`(uuid, 서버 자동) + `daily_log_id`·`user_id`·`vehicle_id`·`work_date`·`sequence`·금액칸·`raw`(jsonb). 앱 항목 id는 `raw.id`에만 있고 고유 조건 없음.
- **키:** `daily_logs`는 (차량, 날짜) 고유 — 같은 날은 차주·기사가 한 줄을 공유. 세 표의 `user_id`가 `profiles`에 `ON DELETE CASCADE`
  → **쓴 사람 계정이 삭제되면 그 사람이 입력한 항목도 서버에서 함께 삭제된다**(공용 장부와 충돌 — 사용자 결정: 고친다, 5-C).

- **항목 id 없는 옛 행(사용자 조회):** 유류 0/2, 정비 **3/6**, 기타 0/1. → 서버 변경 없이, 불러올 때 쓰는 임시 id 계산(`maint-날짜-순번`, `expenseFrom*Record`)을
  저장 때도 똑같이 써서 찾는다. 고치면 `raw.id`가 채워져 이후 고정된다.

### 결정 `[확인: 2026-09-27]`
1. 설계 "연동 차량은 항목 id 기준으로 바뀐 것만 넣고·고치고·지우기" + 슬라이스 2개(5-B-1 기사 쪽 → 5-B-2 차주 쪽).
2. 계정 삭제 시 입력 항목이 함께 지워지는 서버 설정은 **고친다** — DB 변경이라 5-B 뒤 별도 슬라이스 5-C.

## 배포까지 순서 5-B-1 — 기사 쪽 정비/주유/기타를 항목 단위로 저장 `[x]` (착수지시서 확정 2026-09-27)

> 완료(2026-09-30): react-app `f8744dc`, 브라우저 확인·push·CI 초록·§5 리뷰 통과·사용자 최종 승인.

### 1. 목적 (쉬운 말)
연동 기사가 정비/주유/기타를 저장할 때 **바뀐 항목만** 서버에 반영한다. 기사가 저장해도 차주가 그 차량에 넣은 항목이 지워지지 않게 한다.
기사 화면에 들어오는 차주 항목도 기사 본인 매출 비용에 포함한다(5-A-2 한계 해소).

### 2. 현재 → 목표
| | 현재 | 목표 |
|---|---|---|
| 기사 저장 | 배정 차량의 날짜별 항목 **전부 삭제 후 내 목록 재삽입**(`syncExpenseRecords.js`) — 서버가 허락하므로 차주 행도 지워짐 | 서버 행 목록을 읽고 항목 id로 맞춰 **새 것 넣기·바뀐 것 고치기·내가 알던 것 중 뺀 것만 지우기**. 모르는 항목은 안 건드림 |
| 하루 기록 줄 | 없으면 내 일지 내용으로 만들고, 동시에 생기면 덮어쓸 수 있음(upsert) | 없을 때만 만들고 이미 있으면 **안 덮어씀**(충돌 무시 후 다시 읽기) |
| 고칠 때 쓴 사람 | (지우고 다시 넣어 기사로 바뀜) | 고치기에서는 `user_id`를 안 보냄 — 원래 쓴 사람 유지 |
| 기사 불러오기 | 차주가 넣은 항목에 차량 표시가 붙어 기사 본인 매출에서 빠짐 | 기사 세션에서는 차량 표시를 떼고 불러옴 |

차주 저장 경로(메인·미연동 서브의 날짜별 방식)는 **무변경** — 5-B-2에서 연동 서브만 새 방식으로 옮긴다.

### 3. 건드릴 파일 (react-app)
1. `src/lib/syncExpenseItems.js` **(신규)** — 한 차량의 세 종류를 항목 단위로 맞추는 함수. 이전 목록(저장 전 화면 값)·새 목록·차량 id를 받는다. 새 저장소·큐 아님.
2. `src/lib/expenses.js` — 기사 세션(로그인 id ≠ `ownerKey`, `boot.js:59` 기준)이면 배정 차량에 위 함수, 아니면 기존 5-A 경로 그대로.
3. `src/lib/hydrateEmployedDriver.js`(178줄) — `fetchExpensesForAssignedVehicle` 결과에서 차량 표시 제거 1곳.
4. 테스트: `src/lib/syncExpenseItems.test.js`(신규)·`src/lib/cloudMemorySave.test.js`(기사 저장)·`src/lib/hydrateEmployedDriver.test.js`.
   `src/testSupport/fakeSupabaseClient.js` — 가짜 서버의 고치기(update)가 조건(어느 행)을 테스트에 넘기도록 1줄(테스트 전용).

### 4. 안 건드릴 것 (근거)
- `syncExpenseRecords.js`·`expenseVehicleRouting.js` — 차주 경로 전용, 이번엔 호출만 기사 세션에서 안 탐(`expenses.js` 분기).
- 화면 파일 — 저장 창구가 `saveExpenses` 1곳(`MaintFuelPage.jsx:85`·`useExpenseForm.js:42`)이라 화면 무변경.
- 서버(DB) — 권한이 이미 허용(조사 3).

### 5. §8 5대 질문
1. 구독 화면 무변경. 2. 보이는 값 = store(불러온 서버 값). 3. 쓰기 창구 `saveExpenses` 1곳. 4. 동시편집: 항목별로 처리 — 상대가 새로 넣은 건 내가 모르므로 안 지움,
같은 항목을 동시에 고치면 나중 저장이 이김. 5. 권한: 확인됨(결정·조사 3).

### 6. 기대 동작
- 기사가 항목 추가·수정·삭제 → 그 항목만 서버 반영. 같은 차량·같은 날짜의 차주 항목은 그대로.
- 기사 화면의 차주 항목도 기사가 고치고 지울 수 있고(권한), 기사 본인 매출 비용에 포함.
- 항목 id 없는 옛 정비 행도 고치기·지우기가 됨.
- 차주 화면·차주 저장 동작은 지금과 같음.

### 7. 실패 시 처리
기존과 같음: 서버 오류 → 던져서 "저장하지 못했습니다" 토스트, store는 저장 전 값. 부분 성공 후 다시 저장해도 "서버에 없으면 넣기·있으면 고치기"라
중복 없이 이어짐. **신규 레이어(큐·재시도·임시 저장소) 없음.**

### 8. §6 200줄
신규 `syncExpenseItems.js` 150줄 안팎 예상(넘으면 멈추고 보고). `hydrateEmployedDriver.js` 178줄 +1~2줄, `expenses.js` 45줄 +10줄 안팎.
