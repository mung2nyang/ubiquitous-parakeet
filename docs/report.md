# docs/report.md — 현재 슬라이스 착수지시서

## 0-1. 개인정보 화면 로그인 상태 텍스트 입력 오류 — 착수지시서 (작성 2026-09-24, `[확인: 2026-09-24 보리 — 1번으로 진행 요청]`)

지난 슬라이스 ③ 11-5·11-6 착수지시서는 `git show 716576e -- docs/report.md`.

### 1. 현재 상태 (원인) — 코드 읽기로 확인, 브라우저 재현은 아직 안 함

- `PersonalInfoPage.jsx:36-41` `update()`가 **글자를 한 자 칠 때마다** `saveProfile(ownerKey, { ...profile, [field]: value })`를 부른다.
- 입력칸 값은 Store의 `profile`이다(`value={profile.bizName}` 등 12칸). 로그인 상태에선 `profile.js:48-50`이 **서버 저장(`upsertProfileOnSupabase`)이 끝난 뒤에야**
  Store를 바꾼다(2026-09-02 `fbe91d5`부터). 그래서
  ① 친 글자가 서버 응답이 올 때까지 화면에 안 나타나고, ② 빠르게 치면 다음 글자가 옛 `profile` 기준으로 계산돼 앞 글자가 덮여 사라지고,
  ③ 응답 순서가 뒤바뀌면 값이 되돌아간다. 게스트는 서버를 안 거쳐서 정상이다.
- 이 화면 텍스트 입력 12칸(사업자 정보·대표자·연락처·정산 계좌) 전부 해당. 로그인 상태로 글자를 치는 테스트는 지금 없다.
- 플레이북(`docs/testing-playbook.md`) 열람 완료 — 이 화면은 저장·동기화 경로 호출부라 §3 실패 주입·§5 세션 무효화·§6 되돌려 FAIL 확인 적용.

### 2. 목표 (기대 동작)

1. **입력한 글자가 즉시 화면에 나타난다.** 로그인·게스트 모두, 빠르게 쳐도 글자가 사라지지 않는다.
2. **저장은 묶어서 한 번에:** 입력을 멈추고 약 0.7초 뒤, 또는 다른 칸/버튼으로 옮길 때(칸을 벗어날 때), 또는 화면을 나갈 때 —
   그 시점의 값 전체를 기존 `saveProfile`로 저장한다(서버 선행 → Store 반영 순서는 그대로).
3. 저장이 진행 중일 때 새 입력이 생기면 진행 중인 저장이 끝난 뒤 최신 값으로 한 번 더 저장한다(겹쳐 보내지 않음).
4. 저장이 **실패**하면 기존과 같은 토스트("저장에 실패했습니다. 네트워크 상태를 확인해 주세요.")를 띄우고, 입력칸은 저장돼 있는 값으로 되돌린다
   (기존 "실패하면 값이 바뀌지 않는다"와 같음 — 화면 값과 저장 값이 어긋난 채 남지 않게).
5. 다른 곳에서 프로필이 바뀌면(로그인 직후 불러오기 등) **사용자가 지금 치고 있지 않은 칸**은 그대로 따라 바뀐다
   (기존 테스트 `PersonalInfoPage.profileSoT.test.js` 유지). 치고 있는 칸은 사용자 입력이 우선.
6. 화면 표시 규칙은 그대로: 이름·연락처 칸은 프로필 값이 비면 로그인 세션의 이름·연락처를 보여 주고, 연락처는 입력 중 자동 하이픈 서식을 유지.

### 5. §8 확인 5문

1. 구독: 화면은 `useOwnerProfile`(구독) — 유지.
2. 값 출처: 치는 중인 칸은 화면 임시값(draft), 나머지는 Store `profile`(로그인이면 서버 저장 후 Store). localStorage 직접 읽기·쓰기 없음.
3. 쓰기 창구: 기존 `saveProfile`(변경 없음). 배럴 `save*` 우회를 새로 만들지 않음.
4. 겹칠 때: 저장은 한 번에 하나씩(진행 중이면 끝난 뒤 최신 값으로 1회). hydrate가 끼면 치지 않는 칸은 Store 값이, 치는 칸은 사용자 입력이 이김. 화면은 hydrate 중(`useHydrationLock`)이면 기존대로 입력 잠금.
5. 권한: 본인 `profiles` 행만 쓴다(기존과 동일, 변경 없음).

### 6. 실패 시 처리 — 신규 레이어 없음

기존 `saveProfile`의 차단·서버 실패·세션 변경 처리를 그대로 쓴다. 실패 시 Store·localStorage 무변경 + 실패 토스트 + 입력칸을 저장 값으로 되돌림.
**새 큐·재시도·임시 저장소·localStorage 키를 만들지 않는다**(§7). 화면 임시값(draft)은 컴포넌트 안 메모리일 뿐이며 화면을 나가면 사라진다
(나갈 때 저장을 한 번 시도하는 것이 전부).

### 7. §6 200줄

바뀌는 파일 전부 200줄 이하(위 표). 훅을 새 파일로 둔 이유: `PersonalInfoPage.jsx`가 이미 185줄이라 로직을 넣으면 200줄에 근접.

### 8. 검증

- 로컬 `npm test` + `tsc` + strict 진단 새 파일 몫 0 + 수정 코드를 되돌리면 새 테스트가 FAIL하는지 확인(플레이북 §6).
- 테스트 항목(로그인 세션 + 서버 응답을 일부러 늦춘 스텁): ① 빠르게 여러 글자를 쳐도 입력칸에 전부 남고 서버 저장은 **1회**(마지막 값 전체) / ② 저장이 진행 중일 때 추가 입력하면 끝난 뒤
  최신 값으로 1회 더 저장 / ③ 칸을 벗어나면 0.7초를 안 기다리고 즉시 저장 / ④ 화면을 나가면(언마운트) 남은 입력을 저장 시도 /
  ⑤ 서버 실패(throw·`{data:null,error}`)면 토스트 + 입력칸이 저장 값으로 복귀 + Store 불변 / ⑥ 치지 않는 칸은 외부 프로필 변경을 따라감 /
  ⑦ 게스트도 글자가 사라지지 않음 / ⑧ 연락처 하이픈 서식 유지 / ⑨ 기존 `PersonalInfoPage` 테스트(탈퇴·SoT) 그대로 통과.
- **브라우저 검증(보리, 로그인 상태):** ① 사업자명(상호)에 긴 글자를 빠르게 입력 → 글자가 안 사라지고 즉시 보이는지.
  ② 입력을 멈추고 1~2초 뒤 새로고침 → 값이 남아 있는지. ③ 입력 직후 바로 다른 칸을 누르거나 뒤로 가기 → 값이 저장됐는지(새로고침 후 확인).
  ④ 연락처·계좌번호 칸도 같은 방식으로. ⑤ (가능하면) 네트워크를 끊고 입력 후 칸을 벗어남 → 실패 토스트가 뜨고 칸이 이전 값으로 돌아오는지.
  ⑥ 게스트(로그아웃) 상태에서도 정상 입력되는지.

### 9. 확인이 필요한 것 (1개)

- 위 2-4의 "저장 실패 시 입력칸을 저장 값으로 되돌림"은 기존 동작(실패하면 값 안 바뀜)과 같아 안전하다고 판단했다. 다만 **긴 글자를 쳤는데 실패하면 그 글자가 사라진다**는 뜻이다.
  대안은 "글자는 화면에 남겨 두고 토스트만 띄운 뒤 다음 입력 때 다시 저장 시도"인데, 그러면 화면 값과 저장된 값이 어긋난 채로 남을 수 있어 권하지 않는다. 되돌림으로 진행해도 될지 확인 부탁드린다.
